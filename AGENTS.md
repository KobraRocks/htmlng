# AGENTS.md

Guidance for AI coding agents working in **this repository** (the htmlng engine itself).

> If you are instead *using* htmlng to build a site, see `skill/SKILL.md`. If you are
> working on the engine's source, this file is for you.

Judgement calls a reviewer enforces are in [CODING_STANDARDS.md](CODING_STANDARDS.md);
mechanical limits are enforced by `test/architecture.test.ts` and described below.

## What this is

`htmlng` is a deterministic, component-based static HTML generator built for AI agents.
Pages are assembled from isolated component templates plus YAML data. The engine is a
TypeScript CLI; there is no framework and no runtime magic.

- **Language**: TypeScript (strict), ESM, Node ≥ 22.
- **Binary**: `dist/index.js`, published as `htmlng`.
- **Source root**: `src/` (flat, one job per module).
- **Tests**: `test/` (vitest), run against `src/` directly.

## Dev loop

```bash
npm install
npm test              # vitest run
npm run typecheck     # tsc --noEmit
npm run build         # tsc -> dist/ (the CLI binary)
npm run dev:build     # tsc --watch while editing source
```

Rules:
- **Never edit `dist/`** — it is generated by `npm run build` and gitignored.
- **Never edit `build/`** inside a generated project — it is regenerated.
- Keep `npm test` and `npm run typecheck` green. Run both before considering a change done.
- Match the existing style: flat modules, no new dependencies without strong reason,
  explicit `EngineError` with a stable `code`, no frameworks.

## Mechanical limits

`test/architecture.test.ts` enforces three rules over `src/**/*.ts`; `npm test` runs it.

- Every module starts with a `/** ... */` docblock, after an optional shebang. State what
  the module does and who calls it.
- Relative imports may not traverse two or more parent directories (`../../`), in static,
  type, re-export, or dynamic form.
- Files listed in `test/architecture-baseline.json` are ratcheted at their recorded line
  counts. A listed file may not grow, and a shrink requires lowering the baseline in the
  same change. Do not raise a baseline entry; extract code instead. #19's split of
  `cli.ts` retired its entry, so the baseline is empty; the mechanism remains for any
  future oversized module.

The rationale is in
[docs/adr/0001-architecture-guardrails.md](docs/adr/0001-architecture-guardrails.md).

## Golden path (the primary agent workflow)

```bash
htmlng context                          # discover pages, components, data, tokens (JSON)
htmlng create component hero            # scaffold a component
htmlng create page index                # scaffold a page
htmlng add component hero --page index  # wire it into the page
htmlng create data hero --page index    # scaffold a data file from the schema
# edit components/hero.component.html and data/index/hero.yaml
htmlng render component hero --page index   # tight per-component check
htmlng render page index                    # full assembly check
htmlng validate                             # gate: exits 1 on any error
htmlng build                                # write build/
```

## Invariants (do not violate)

1. **Component templates are inner content only.** The engine emits the semantic
   wrapper from the component **name** (`header` → `<header>`, `footer` → `<footer>`,
   everything else → `<section id class>`; position never decides the tag). Do not add a
   wrapper `<div class="<component-name>">`; the validator warns (`COMPONENT_REDUNDANT_WRAPPER`).
2. **Component files have three sections separated by lines containing only `---`**:
   template, optional CSS, JSON schema. An empty CSS section is allowed.
3. **No `<script>`, `<style>`, or `style="..."` in a component template.** Scripts go in
   the page YAML (end of `<body>` by default, or `<head>` with `head: true`); styles go in
   the CSS section (auto-scoped under the component class, except `html`/`body`/`:root`/`:host`
   first compounds and selectors led by `:global(...)`, which stay unscoped; a `:global(...)`
   later in a selector exempts only the wrapped compound).
4. **Every template placeholder must exist in the schema, and vice versa** (the latter
   is a warning). `text` fields allow only the inline whitelist. `if`/`unless` blocks share
   the component scope; `list` item fields do not.
5. **Data files** are a YAML map (one instance) or a sequence (repeat the whole component,
   ids `<name>-0`, `<name>-1`, …; schema stays flat). A nested `item` schema is unsupported.
6. **Page files are layout only** — title, description, ordered component list, optional
   `layout` (`wrapper`/`bodyClass`), `head`, and `scripts`. The engine always emits
   `<body class="<page>" data-page="<page>">`.
7. **Element placeholders are content, not attributes** — `{{image:x}}`/`{{link:x}}`/`{{slot:x}}`
   emit a whole element; inside an attribute value they are a `COMPONENT_PLACEHOLDER_IN_ATTRIBUTE` error.
8. **Output is a pure function of sources.** Do not introduce nondeterminism.

## Discovery before guessing

| Need | Command |
|---|---|
| What pages/components/data exist, tokens, staleness | `htmlng context` |
| File formats, placeholder data shapes | `htmlng schema` |
| Meaning of an error code + fix | `htmlng explain <CODE>` |
| List resources | `htmlng list pages\|components\|data <p>\|presets` |
| Assembled CSS for a page | `htmlng css <page>` |

## Machine-readable output

Add `--json` to any command for a single JSON object on stdout stamped with
`schemaVersion`. Errors carry a stable `code`:

```bash
htmlng --json validate
# { "schemaVersion": 1, "ok": false,
#   "errors": [{ "code": "SCHEMA_VALIDATION", "level": "ERROR", "file": "...", "message": "..." }],
#   "warnings": [] }
```

Exit codes: `0` success, `1` any failure. Prefer `--json` over parsing prose.

## Errors

For the meaning and fix of every diagnostic code, run `htmlng explain <CODE>` (backed
by `src/error-catalog.ts`). This file keeps no error catalogue of its own.

## Testing conventions

- Unit tests import the module under test; CLI tests call `run(argv, ioSink)` with a
  captured sink and assert on the returned exit code plus stdout/stderr.
- CLI tests `process.chdir()` into a `mkdtempSync` fixture project and restore cwd after.
- Long-running commands (`watch`, `serve`) never return from `run()`; spawn the real
  entry point (`test/serve-watch.test.ts`) and assert on stdout/stderr instead.
- Error tests assert `EngineError.code` where relevant.
- `test/docs.test.ts` keeps README/SKILL/HELP in sync with the command list — update the
  docs when you add a command, or that test fails.

## Where to make a change

| Change | File(s) |
|---|---|
| New CLI command | a new single-purpose module for the handler (or an existing `commands-*.ts` family), wired into `src/cli.ts` (`handlers` map + `HELP`), `README.md` table, tests |
| New placeholder type | `src/types.ts`, `src/schema.ts`, `src/template.ts`, `src/format-spec.ts`, `src/component.ts` |
| New error | `src/error-catalog.ts` + throw with that code |
| Validation rule | `src/validator.ts` / `src/schema.ts` / `src/text-validator.ts` |
| Diagnostics policy | `src/diagnostics.ts` |
| CSS scoping | `src/css.ts` |
| Output shape | `src/renderer.ts` |
